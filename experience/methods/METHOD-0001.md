# 三阶段 AI 协作研发：从反复迭代到一轮完整交付（V3.0）

> **适用对象**：没有编程或运维经验、但希望通过 AI 编程工具持续交付软件的产品经理。
> **性质**：通用协作方法总结，不包含实际项目的代码、机构、业务资料、运行日志、私有仓库或客户信息。
> **公开范围**：仅收录于公开 GitHub 仓库，尚未申请网站展示。

## 问题：为什么 AI 编程很容易越做越复杂？

产品负责人使用编程 Agent 后，仍可能陷入：需求尚未定稿就开始改代码、同类功能被拆成许多小任务和 PR、每次修复都重复文档治理，以及用“代码已推送”替代“产品已验收”等问题。

更高效的方案不是堆叠更多角色和工具，而是明确三阶段分工、一次完成同类功能，并保留真实测试和人工验收。

**核心原则：三阶段、一轮一交付、多 Agent 可选、集中研发测试、人工验收、GitHub 存事实。**

## 阶段一：产品定义与研发准备

**责任人：产品负责人 + ChatGPT。**

完成需求讨论、目标与边界、冻结方案、验收标准和回退要求。一次性把必要材料整理入 GitHub，形成编程 Agent 可以独立接手的任务；Issue 按需创建，不要求每个小改动都产生一组文档。

**交付：** 冻结需求、验收清单、版本边界、明确研发任务及可信源码基线。

产品负责人回答“做什么、为什么做、哪里不能改”；ChatGPT 负责将决定整理成可验证的交付规则，而不是提前扩大工程范围。

## 阶段二：集中研发与自动化测试

**执行主体：Codex 本地 / ChatGPT Chat 等编程 Agent。**

具备代码工作区和执行权限的 Agent 在**完整源码目录**里集中开发、运行测试、修复缺陷。GitHub 管分支、PR、代码历史及验收证据，不参与每一个编辑动作；同类功能原则上一轮整合交付一个 PR，研发中不反复开展单独的文档治理。

**交付：** 完整功能分支、对应 Commit SHA 的测试命令及结果、明确遗留问题、一个待验收 PR。

必须区分 `PASS`、`FAIL`、`BLOCKED`、`NOT_RUN`。对涉及交互的产品，不能只测 API 或菜单能否点击，还应运行适用的浏览器、兼容和失败路径测试。代码提交并不表示已通过验收。

编程工具**不绑定单一产品**：只要实际能够访问完整工程、执行测试并交付可追溯证据，Codex、ChatGPT Chat 或其他 Coding Agent 都可以承担本阶段。

## 阶段三：本地人工验收与版本收口

**责任人：产品负责人 + ChatGPT + 编程 Agent。**

产品负责人在本地运行**PR 分支对应的版本**，核对业务流程、操作体验及验收标准。ChatGPT 独立复核差异，Agent 在原 PR 分支修复已确认的问题；通过后由产品负责人授权合入 `main`。

**交付：** 已验收的稳定主线、合并与测试证据、必要的版本记录、下一轮可信起点。

不能在旧 `main` 上体验后判断新版没有改动；也不能凭绿色 CI 替代人工产品验收。未合并、未测试、已测试、已发布是四种不同状态，应分别记录。

## 五项执行规则

1. **同类功能集中完成**：按完整业务目标组织研发；仅在安全边界、依赖或明确独立验收需要时才拆轮。
2. **工具不绑定，责任要固定**：产品负责人决策、ChatGPT 讨论与验收、编程 Agent 研发测试、GitHub 保存最终事实。
3. **测试前置，证据绑定提交**：自动化、浏览器、兼容及异常检查按适用范围执行；重新提交后确认所测 SHA，失败就修，未执行就写 `NOT_RUN`。
4. **额度不足不等于可以跳过测试**：当托管 CI 无法运行时，由可信本地环境执行等效测试并保留日志；不得伪造 CI PASS，高风险变更没有必要证据时仍应阻断合并。
5. **减少过程治理**：只在准备阶段冻结关键需求，交付阶段更新必要状态和交接；不为每个编码动作增添 Issue、PR 或冗余文档。

## 零编程产品经理的操作要领

- **开始前**：要求 ChatGPT 用可理解的语言明确“目标、不能改的地方、怎么判断完成”，让 Agent 从仓库最新状态启动。
- **研发中**：重点查看功能演示、失败清单、测试日志和可操作的验收版本，不必逐行指导 Agent 修改代码。
- **验收时**：通过本地同步工具获取正确研发分支，再启动、体验、截图、反馈；明确要求失败项仍在原 PR 内收口。
- **合并后**：检查真实 `main` 和交接记录，下一轮从 GitHub 重新恢复上下文，而不是仅根据长对话猜测工程状态。

## 能得到什么，不能宣称什么

这种方法减少重复沟通、碎片化 PR 和无效文档工作，适合小团队以及产品经理主导的 AI 编程协作。但“效率提升”是定性的流程经验，**没有量化工时、成本或质量提升数据**，不得写成已实测的百分比。

方法不能替代权限控制、敏感数据合规、专业领域审查、生产安全验证和正式发布审批。

## 脱敏与发布边界

本方法只保留已确认可公开的抽象流程，不公开任何可反查具体项目的名称、内部版本、仓库、组织、客户信息或生产配置。个人或机构授权证据如有需要，应保存在合规的非公开位置。

**仓库收录不等于网站上线**：本方法的 `website_review` 为 `not_requested`，不加入 Pages 展示白名单；如需网站展示，必须另行完成审核。
