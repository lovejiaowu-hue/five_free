# GitHub 中文使用手册：产品经理与 AI 协作开发版

> **版本**：2026-10-30 · **语言**：英文界面 / 中文讲解  
> **适用**：零编程基础、熟悉 Discuz/站长后台、使用 ChatGPT / Codex 等工具协作开发的产品经理。  
> **范围**：基于用户提供的 GitHub 三张截图（全局导航、仓库 Code 页、Settings → General 页），扩展到常用一级/二级菜单与实际操作流程。  
> **提醒**：GitHub 持续改版；有些菜单随个人/组织仓库、账户套餐及功能开关不同而变化。本文的中文是便于理解的译法，不一定与 GitHub 官方简体中文帮助中心逐字一致。**不要把仓库设为 Public 来解决代码无法部署、自动测试未通过等问题。**

## 01. 先建立整体概念

GitHub = **代码资产仓库 + 版本管理系统 + 开发协作平台 + 自动化测试/发布平台**。

| GitHub | 中文 | Discuz / 网站运营 / 产品经理类比 | 什么时候用 |
|---|---|---|---|
| Repository / Repo | 仓库 | 一个独立网站/插件的完整项目档案 | 管理源码、素材、文档、版本 |
| Branch | 分支 | 独立开发副本/候选版本线 | AI 或同事做新功能，不干扰正式版 |
| Commit | 提交记录 | 每一次明确的内容存档和修改履历 | 追踪“谁在何时改了什么” |
| Push | 推送 | 将本地修改同步至云端 GitHub | Codex 本地开发完成后备份成果 |
| Pull / Fetch | 拉取 / 获取 | 同步云端的最新改动到本地 | 开工前获得当前项目基线 |
| Pull Request / PR | 合并请求 | 开发成果的验收审批单 | Review 之后才允许进入主线 |
| Merge | 合并 | 审核通过后入主版本 | 将已验收功能纳入 main |
| Issue | 问题 / 任务单 | 功能需求、Bug、优化工单 | 安排、指派、追踪任务 |
| Project | 项目看板 | 产品研发任务大盘 | 管理多人多仓库进度 |
| Actions | 自动化工作流 | 自动测试、构建、发布流水线 | 每次提交自动验收基本质量 |
| Releases | 正式发行版 | 插件安装包、定稿版本归档 | 让运营/客户拿到稳定交付包 |
| Pages | 静态网站托管 | 前端页面的在线展示空间 | 产品 Demo、纯前端站点、说明文档 |
| Settings | 仓库设置 | 站长后台/项目管理员配置 | 权限、安全、默认分支、发布 |

**特别区分四件事**：

1. **Commit 成功**：修改被记录在某个仓库/分支的历史里；不等于已同步云端。
2. **Push 成功**：提交已到 GitHub 的某个分支；不等于进入 `main`。
3. **PR Merge 成功**：变更进入目标分支（常见为 `main`）；不等于已部署上线。
4. **Deployment/Pages 成功**：部署任务成功，仍需实际访问网址并完成功能验收。

| MCP registry | MCP 服务目录 | 找 Agent 使用的 MCP 工具服务；与项目仓库本身不同。 |
| Top repositories | 常用仓库 | 经常访问的仓库快捷列表。 |
| Show more | 展开更多 | 显示更多仓库快捷入口。 |
| Search or jump to... / Type `/` to search | 搜索或快速跳转 | 可搜索仓库、代码、Issues、PR；按 `/` 常可聚焦搜索框。 |
| New repository | 新建仓库 | 创建一个新的项目；适合每个独立产品/插件拥有清晰边界。 |
| Your profile | 个人资料 | 开发者个人页面、贡献动态、项目概览。 |
| Your repositories | 我的仓库 | 查看本人名下仓库，区别于参与的其他人的项目。 |
| Notifications | 通知 | 查看提及、PR 审核请求、任务进展。 |

### 全部仓库页常见操作

| 英文 | 中文 | 实际作用 |
|---|---|---|
| Repositories | 仓库列表 | 所有可访问项目的目录（可筛选）。 |
| Private | 私有仓库 | 仅获授权的人能够查看仓库内容。 |
| Public | 公开仓库 | 互联网上任何人可以读取可见内容；**不能当保密存储**。 |

| Recently updated / Updated | 最近更新 | 看哪些仓库最近有活动。 |
| List view / Grid view | 列表/卡片视图 | 改变展示形式，不改变仓库内容。 |
| Repository settings（齿轮） | 仓库设置 | 对指定仓库进行管理操作。 |

## 04. Code：代码主页（截图二）

**用途**：查看完整文件树、切换分支、下载源码、查看历史。即使不会编程，也应该能读懂此页。

| 英文 UI | 中文 | 作用 / 注意 |
|---|---|---|
| Code（顶部标签） | 代码 | 整个仓库的文件与源码总览。 |
| `main` | 主分支 | 该项目当前默认的主线；**名称不必定为 main**，也可能是 master。 |
| Branch selector | 分支选择器 | 切换到某个开发分支，查看候选代码。 |
| 1 Branch / Branches | 分支数量/列表 | 查看仓库有多少条开发线、谁在做什么。 |
| 0 Tags / Tags | 标签数量/列表 | 查看标记过的版本节点，如 `v1.2.0`。 |
| Go to file | 查找文件 | 输入文件名快速定位，如 `README.md`、`AGENTS.md`。 |
| Add file | 添加文件 | 展开可选择创建文件、上传文件。 |
| Create new file | 新建文件 | 用网页直接新增 MD、配置或小型源码文件。 |
| Upload files | 上传文件 | 上传本地文档或代码。注意大批量源码优先交给 Codex/Git 管理。 |
| **Code（绿色按钮）** | 获取代码 | 展开克隆链接、下载 ZIP、桌面工具等。与顶部 Code 页面标签并非同一个按钮。 |
| Clone / HTTPS | 克隆 / HTTPS 地址 | 将整套 Git 历史复制到本地，适合持续开发。 |
| Open with GitHub Desktop | 使用 GitHub Desktop 打开 | 图形化 Git 客户端，不用每次手输命令。 |
| Download ZIP | 下载压缩包 | 获取当前选定分支的文件快照；**通常不含完整 Git 版本历史**，不适合日常协作。 |
| Latest commit | 最近一次提交 | 查看最新变更摘要及对应编号。 |
| Commit hash（如 027055d） | 提交标识 | 某一次变更的唯一标识（界面常显示缩写）；排查问题时非常有用。 |
| 118 Commits / History | 提交历史 | 看每次代码改动。可比较差异、定位引入问题的时间。 |
| Browse files | 浏览文件 | 进入目录或打开文件。 |
| Edit this file（铅笔） | 编辑文件 | 直接在网页编辑文件；可能直接提交到当前分支，操作前看清目标分支。 |
| Raw | 原始文件 | 查看原始纯文本或原始文件内容。 |
| Blame | 逐行修改追踪 | 查每行代码最近是谁、何时改过；定位缺陷尤其有用。 |
| History | 文件历史 | 只查看这个文件的历次修改。 |
| View file / Preview | 查看文件/预览 | 例如 Markdown 的阅读视图。 |
| Watch | 关注通知 | 选择订阅仓库活动；不等于收藏。 |
| Fork | 派生仓库 | 创建可独立修改的仓库副本；团队内多人协作通常优先 Branch，而非每人 Fork。 |
| Star | 收藏/点赞 | 标记喜欢的项目，不授予访问权限。 |
| About | 项目简介 | 仓库介绍、网站链接、技术标签。你的截图此处提示尚未填写。 |
| Edit repository details（齿轮） | 编辑仓库资料 | 设置描述 Description、网站 Website、Topics。 |
| README | 项目说明 | 仓库的首页说明书，适合写产品介绍、运行方法、当前版本与负责人。 |
| Activity | 项目活动 | 查看近期仓库动态。 |
| Releases | 正式发行版 | 归档封版版本，附下载包和更新说明。 |
| Packages | 软件包 | 分发程序库、容器镜像等，和 Releases 的最终压缩包不同。 |
| Contributors | 贡献者 | 查看参与开发并产生可归属提交的人。 |
| Languages | 编程语言分布 | 粗略了解项目的技术组成，不代表功能成熟度。 |

### 常见仓库文件名

| 文件/目录 | 中文解释 | 管理建议 |
|---|---|---|
| `README.md` | 项目首页说明 | **每个仓库都要有**，特别说明项目定位和如何启动。 |
| `AGENTS.md` | 给 AI 开发代理的工作约束 | 写明不可覆盖、测试、分支、目录和交付规范。它是项目约定，不是 GitHub 通用权限开关。 |
| `docs/` | 设计、版本、API、验收文档 | 产品经理的关键资产。 |
| `.github/workflows/` | Actions 自动化流程 | 预先定义代码检查、打包、部署。 |
| `.github/ISSUE_TEMPLATE/` | 需求/Bug 工单模板 | 让提交任务的同事把复现步骤、验收标准写完整。 |
| `.github/PULL_REQUEST_TEMPLATE.md` | PR 审核模板 | 要求列出功能、风险、测试、截图与回滚计划。 |
| `.gitignore` | Git 忽略清单 | 避免上传临时文件、依赖目录、敏感本地配置；**忽略清单不能删除已经提交的秘密**。 |
| `LICENSE` | 开源授权协议 | Public 不等于已经授予他人任意使用权；开放使用要明确许可。 |
| `package.json` | JavaScript 项目配置 | 管理依赖、运行、测试、构建命令。 |
| `.env.example` | 环境变量示例 | 只放字段名和无敏感信息的示例；真正的 `.env` 不应入库。 |
| `src/`, `pages/`, `components/`, `assets/` | 源代码、页面、组件、素材 | 常见项目目录，具体含义由项目约定决定。 |
| `dist/`, `build/` | 编译输出 | 可能用于部署，不一定应提交源仓库。 |

### 三个容易混淆的动作

- **Download ZIP**：下载一次性的源代码快照，通常不能保留完整版本管理能力。
- **Clone**：将仓库包括 Git 历史及版本关系复制到本地，适合长期协作。
- **Fork**：在 GitHub 上生成一个与原项目关联的独立仓库副本，适合外部贡献，不是常规的项目分支。

## 05. Issues：产品任务与 Bug 管理

建议使用方式：**一个 Issue = 一个可验证的任务结果**，而不是一整轮无法验收的大项目。

| 英文 | 中文 | 实际用途 |
|---|---|---|
| New issue | 新建问题/任务 | 提出功能、Bug 或运营优化要求。 |
| Title | 标题 | 简洁描述问题，如“签到手机号授权后找不到机构”。 |
| Description | 描述 | 背景、需求、界面、预期、验收标准。 |
| Open / Closed | 待处理 / 已关闭 | 管理工单生命周期，关闭不一定代表已发布上线。 |
| Assignees | 负责人 | 指派给开发者或可用的 Agent。 |
| Labels | 标签 | 如 `bug`、`feature`、`urgent`、`needs-review`。 |
| Milestone | 里程碑 | 例如 `V2.1 RC1`，集中看版本内任务完成度。 |
| Projects | 所属项目看板 | 把工单放到产品计划总表。 |
| Linked pull requests | 关联 PR | 看任务由哪个代码变更解决。 |
| Sub-issues | 子任务 | 将大的开发事项拆成可检查的小项。 |
| Dependencies / Blocked by | 前置依赖 / 被阻塞 | A 任务必须先于 B，避免开发顺序混乱。 |
| Comments | 评论 | 产品补充、开发答复、验收反馈都留在工单里。 |
| Templates | 任务模板 | 统一收集需求/问题信息。 |
| Close issue | 关闭任务 | 确认无需处理或已完成；必要时可 Reopen。 |
| Reopen issue | 重新打开 | 已关闭但复发、验收不通过。 |

**推荐 Issue 模板**：现状 → 目标 → 修改范围 → 禁止改动范围 → 验收标准 → 测试环境 → 附件/截图。你可以把它直接作为给 Codex 的任务输入。

## 06. Pull requests：审核并合入开发成果（极重要）

把 PR 当成**“开发成果验收单”**。开发同事/AI 在独立分支做完，并不意味着可以立即上线。

| 英文 | 中文 | 如何理解 |
|---|---|---|
| New pull request | 新建合并请求 | 把开发分支的成果提交审核。 |
| Base | 目标分支 | 最终要合入哪里，通常是 `main`。 |
| Compare / Head | 来源分支 | 哪条开发分支提出了这些变更。 |
| Open | 审核中 | 还没合并。 |
| Draft | 草稿 | 还在开发中、暂不请求正式审查。 |
| Ready for review | 提交审核 | 告诉负责人已经可以检查。 |
| Conversation | 讨论 | 查看改动说明、评论、批准/驳回。 |
| Commits | 提交记录 | 查看这次任务产生了哪些修改。 |
| **Files changed** | 变更文件 | 最重要的验收入口，查看新增、删除和修改的代码/文档。 |
| Checks | 自动检查 | 测试、构建、代码扫描结果，不等于产品验收。 |
| Reviewers | 审核人 | 指定需要审核的人。 |
| Review changes | 审核改动 | 审核者提交审查意见。 |
| Comment | 评论 | 给意见，但不构成正式通过。 |
| Approve | 批准 | 审核同意；是否可合并仍取决于规则和检查。 |
| Request changes | 要求修改 | 产品验收不通过、需要开发者返工。 |
| Resolve conversation | 标记讨论已解决 | 将已处理的审查意见收口。 |
| Merge pull request | 合并 PR | 将来源分支合入目标分支。 |
| Squash and merge | 压缩后合并 | 将此次 PR 的多个小提交整理成一个提交；适合一任务一 PR。 |
| Rebase and merge | 变基后合并 | 保持较线性的提交历史；新手不用优先选。 |
| Close pull request | 关闭 PR | 不合入，放弃本次请求。与 Merge 不同。 |
| Delete branch | 删除分支 | 合并之后清理已完成的临时分支；先确认分支无其他未合入工作。 |
| Revert | 撤销改动 | 新建反向修改来取消先前合入的内容，常用于故障回退。 |
| Merge conflict | 合并冲突 | 多人改了相同位置，Git 不知道该保留谁的版本；必须人工/AI 仔细判断。 |

**每天验收重点**：目标分支是否正确；改动是否越界；有没有删除/覆盖历史文件；Actions 是否通过；真实界面与功能是否满足需求；是否存在数据库迁移、配置或部署风险。

**最佳实践**：`main` 主线 → `feat/具体任务` 分支开发 → Commit + Push → PR → Checks + 人工验收 → Merge → Release / Deploy。GitHub 官方将 PR 视为提出、讨论、审查及合并代码的核心协作手段。

## 07. Agents：GitHub Agent 任务（截图二）

GitHub 的 **Agents** 标签是 GitHub Copilot/相关 Agent 工作任务的入口，适合让具备相应权限的 AI Agent 在指定仓库里处理工作。**它不等于 ChatGPT 或你本地的 Codex 自动拥有该仓库的全部操作权限**。

| 英文 | 中文 | 意义 |
|---|---|---|
| Agents | Agent 任务 | 启动、查看仓库内 Agent 开发会话。 |

#### 牢记三类身份凭证

- **GitHub App authorization（应用授权）**：授权某个应用代表你访问特定仓库。定期检查其权限与仓库范围。

## 15. Pages：如何把源码发布成一个可打开的网站

**Pages = 静态网页托管，不是完整的云服务器。** 适合 HTML/CSS/JavaScript、静态文档、纯前端 Demo；不能直接作为传统 PHP + MySQL/Node 服务端应用的运行环境。

| 英文 | 中文 | 怎么理解 |
|---|---|---|
| Settings → Pages | 网站发布设置 | 进入当前仓库的 Pages 配置。 |
| Build and deployment | 构建与部署 | 选择网站如何构建、发布。 |
| Source | 发布来源 | 分支（Deploy from a branch）或 GitHub Actions。 |
| Deploy from a branch | 从分支部署 | 选择如 `main` + `/(root)` 或 `/docs` 目录发布静态页面。 |
| GitHub Actions | 通过 Actions 发布 | 构建 SPA/框架项目后自动发布。 |
| Branch | 发布分支 | 哪条分支的内容用于网站发布。 |
| Folder | 发布目录 | 仓库根目录或 `/docs` 等可选路径。 |
| Save | 保存 | 保存网站发布配置。 |
| Visit site | 访问网站 | 打开已发布站点。 |
| Custom domain | 自定义域名 | 绑定自己的域名，需配置 DNS。 |
| Enforce HTTPS | 强制 HTTPS | 使用 HTTPS 访问网站。 |
| Deployment | 部署 | 检查发布任务是否成功。 |

例如你熟悉的 `https://lovejiaowu-hue.github.io/supercare/`，就是**项目 Pages 类型**的典型地址格式。需要重点区分：

1. **GitHub Free**：Pages 通常可用于公开仓库；若要直接从私有仓库启用 Pages，须核对 Pro/Team 等套餐支持。
2. **Pages 网站可能公开**：官方明确指出 Pages 网站即使从支持的私有仓库发布，通常也面向互联网公开访问；私有仓库≠私有网页。
3. **源码和网站分仓库**：如果要私有主源码 + 公开 Demo，可把必要的、无机密的编译后静态产物发布到独立公开仓库。
4. **静态网站不等于 SaaS 后端**：需要数据库、服务端 API、账号体系时，必须另配合适的后端托管与安全控制。

## 16. Releases、Tags、Packages：封版的三种概念

| 英文 | 中文 | 作用 | 建议 |
|---|---|---|---|
| Tag | 版本标签 | 标记 Git 历史上的某个节点 | 如 `v1.2.0`、`v2.0.0-rc1` |
| Release | 正式发行版 | 基于版本标签建立发布页和说明 | 写发布日期、变更内容、已知问题、校验结果 |
| Release assets | 发行附件 | 附上 ZIP、插件安装包、PDF、其他产物 | 让非程序员直接获得安装包 |
| Draft a new release | 起草发行版 | 建立待正式发布的版本记录 | 完成验收再 Publish |
| Pre-release | 预发布版 | 标识候选测试版 | RC、Beta、内部候选版 |
| Latest | 最新正式版标记 | 仓库对外展示的最新 Release | 确认基线后再标记 |
| Packages | 软件包/镜像仓库 | 发布软件依赖包或容器镜像 | 根据技术栈选择，不是必需 |

**你的项目建议使用三个层次**：`dev`/功能分支进行迭代 → `RC` 候选测试 → 正式 `Release` 发布。**Tag/Release 的创建不自动说明实际服务器已更新。**

## 18. 六套标准操作流程：产品经理直接照做

### A. 新建一个产品主仓库

1. `All repositories → New repository`。
2. 填 `Repository name`（如 `aihys-tools`）、`Description`（一句话概述）。
3. 选 `Private`（涉及尚未公开的代码或商业项目时的默认建议）。
4. 初始化 `README.md`，按项目需要选 `.gitignore` 和 `LICENSE`；不公开开源时无需随意添加开放许可。
5. 仓库建立后确认 `main` 或其他既定默认分支。
6. 追加 `AGENTS.md`、`docs/`、任务模板、PR 模板。
7. 配置所需协作者；确认有无保密、测试与发布要求。

### B. 让同事或 Codex 从独立分支交付功能

1. 在 `Issues` 创建一个需求，写明**目标、允许修改的目录、禁止改动范围、验收标准**。
2. 开发者在本地从最新 `main` 建立 `feat/短任务名` 分支。
3. Codex 修改代码、运行项目约定测试，保留测试报告。
4. `Commit → Push` 开发分支；不直接改主线。
5. 创建 `New pull request`，设置 `base: main`、`compare: feat/xxx`。
6. Review `Files changed`、`Checks`、截图/产品体验，必要时 `Request changes`。
7. 验收后才 `Merge pull request`；随后按需清理临时分支。
8. 如为封版版本，创建 `Tag + Release`，写版本说明并提供打包件。

### C. Bug 管理到修复验收

1. `Issues → New issue`：放复现步骤、截图、预期/实际行为。
2. 设置 `Label: bug`、优先级和负责人。
3. 在专用分支修复，PR 关联该 Issue。
4. `Actions` 自动检查；在目标浏览器/设备手工复测。
5. 合并、发布后关闭 Issue；如再次出现则重新打开。

### D. 做公开 Demo，不公开核心源码

1. 将完整版源码保存在 **Private** 主仓库。
2. 在本地完成构建，检查公开产物里没有密钥、商业数据、源映射文件中的敏感信息。
3. 将必要的 HTML/CSS/JS/图片产物同步至专用 **Public** 发布仓库。
4. 公开仓库 `Settings → Pages` 选择发布源。
5. 发布完成访问 `Visit site`，完成 404、图片、移动端、静态路由等复测。
6. 更新主仓库文档里的 Demo 地址与版本映射。

### E. 正式版本发布/回退

1. 发布前锁定**验收通过的准确 Commit**，记录标签和构建产物。
2. `Create new release` → 指定 Tag → 发行说明 + 安装包 → Publish。
3. 独立进行服务器/商店/插件平台的真正部署，并完成冒烟测试。
4. 若发生故障，优先根据预先准备的回退方案恢复上一稳定 Release；不轻易对共享主线执行 `force push` 或历史重写。
5. 记录故障原因和验证证据。

### F. 邀请其他运营同事协作

1. `Settings → Collaborators` 邀请指定 GitHub 用户。
2. 对方接受邀请后才能协作；按项目需要选择最小权限（个人/组织仓库可能不同）。
3. 要求开发均从分支 + PR 进入，不允许把“有写入权限”理解为“可任意覆盖主版本”。
4. 项目交接或人员离开时移除访问、审查 GitHub App/令牌/部署密钥，并交接未合并 PR。

## 19. 仓库安全操作分级

| 风险 | 典型操作 | 建议 |
|---|---|---|
| 低 | Browse files、Go to file、查看 Issues/PR/Logs/History | 可放心查看，都是只读活动。 |
| 中 | New issue、Comment、Star、Watch、下载 ZIP、创建分支 | 确认目标仓库与内容；注意评论可能暴露信息。 |
| 高 | Merge PR、Publish Release、改 Pages 发布源、开通外部 App 写入权限 | 必须有验收/授权与回退计划。 |
| 很高 | Change repository visibility、Delete repository、Transfer ownership、force push、删除 main、覆盖密钥、把生产数据提交入库 | 不要在没有备份、权限审查及影响分析时操作。 |

**私有并不等于绝对安全**：任何有权限的人、被授权的应用、泄露的令牌、错误发布流程都可能带来风险。尤其不应把生产患者/会员/采销数据直接放入 GitHub 仓库或公开静态页面。

## 22. 给你当前项目群的最低可行治理方案

你正在管理多条产品线，且已有 Codex 本地开发习惯。建议先只统一以下规则，不急着建设过于复杂的 GitHub 组织体系：

1. **一产品线一主仓库**：主仓库存正式基线；试验性 3D 场景/原型可以另设 Lab 仓库，定稿再合入。
2. **每仓库只有一个明确的主分支**：通常 `main`；已有 `master` 的仓库不必为了统一而仓促改名。
3. **每轮任务单独分支和 PR**：避免两个 Codex 任务同时写入主分支相互覆盖。
4. **正式交付看 Release，而不看“最新提交”**：Discuz 插件安装包、静态网站 Demo、文档均应标明对应版本和 Commit。
5. **一个最小 README + AGENTS.md + 验收记录**：文档中记清“怎么启动、怎么测试、谁确认、哪个版本”。
6. **Private 默认，公开发布审查**：对外只公开经过检查的演示产物和必要文档。
7. **测试必须真实运行**：只看 Actions 绿色或 Codex 说“已完成”都不够。必须按 PC/H5/微信/安装平台实际复测。

### 建议的目录骨架

```text
repository/
├─ README.md                         项目定位、启动与最新定稿说明
├─ AGENTS.md                         Codex / AI 开发约束
├─ docs/
│  ├─ PRODUCT_SCOPE.md               产品范围与非目标
│  ├─ VERSION_HISTORY.md             版本记录
│  ├─ ACCEPTANCE_CHECKLIST.md        业务验收清单
│  └─ DEPLOYMENT_GUIDE.md            部署与回滚说明
├─ .github/
│  ├─ ISSUE_TEMPLATE/                工单模板
│  ├─ PULL_REQUEST_TEMPLATE.md       PR 验收模板
│  └─ workflows/                     自动测试/构建/发布
└─ src/ or project-specific dirs      实际源代码（按技术栈规划）
```

## 23. 十个常见疑问

**Q1：仓库设为 Private，ChatGPT/Codex 就一定无法访问吗？**  
不一定。只要相关应用有正确授权且工具/连接支持，私有仓库也可读取或写入。**不要把“Private”理解为“只允许浏览器账号自己访问”**。

**Q2：把同事加为 Collaborator，对方能不能改主分支？**  
取决于仓库类型、具体权限以及实际启用的保护规则。拥有写入能力且缺少有效主线保护时，可能直接更改主分支。应通过权限与 PR 流程共同管理。

**Q3：`main` 是正式环境吗？**  
`main` 是代码分支。正式环境是运行程序的服务器、站点、应用商店或部署系统；两者只有配置了发布关系才会关联。

**Q4：Commit / PR / Release 有什么区别？**  
Commit 是改动记录；PR 是变更审核；Release 是对外可识别的版本发布。三者不同。

**Q5：GitHub Pages 能运行 Discuz X5 吗？**  
不能直接运行其 PHP、MySQL 服务端。只能发布静态展示页面；Discuz 需能运行 PHP 和数据库的服务器环境。

**Q6：一个仓库能放多个插件吗？**  
可以，属于 monorepo（单仓多项目），但需清晰目录、独立打包与权限流程。不同负责人并行时避免互相覆盖。不是所有项目都必须拆仓。

**Q7：同一个项目是否需要测试和正式两个仓库？**  
通常不必。用分支、环境和 Release 就能分离大部分流程；若要公开 Demo 但保留核心源码私有，双仓库非常有意义。

**Q8：PR 自动检查绿色能直接发布吗？**  
不能。自动检查只证明已配置的检查通过，不保证产品体验、业务逻辑和运行环境无问题。

**Q9：删除分支会不会删除已经合入主线的功能？**  
一般不会影响已合入的代码，但删除前应确认所有变更都已合并且没有其他依赖。

**Q10：什么是最低限度的备份？**  
GitHub 云端仓库不能代替独立备份。对重要项目要保留明确版本 Tag/Release、可恢复的源码镜像或定期离线备份，以及数据库另行备份。

## 24. AI 协作编程实战：从产品需求到 CI、部署、验收（2026-11 新增）

> **本章来源**：将一次私有家庭健康应用的「产品负责人 + ChatGPT」协作研发过程改写为通用教学案例。**不包含真实患者身份、病历、私有项目地址、账号密码或服务器配置**；案例中的状态用于解释工作流，不是任何产品当前的上线公告。
>
> **适合谁**：不会写代码，但需要独立担任产品负责人，用 ChatGPT / AI Agent + GitHub 研发、测试、发布产品的人。
>
> **术语原则**：GitHub 官方功能（Issue / PR / Actions）与团队自建工程制度（PRD / ADR / 轮次账本 / 交接）是两类东西，不要混为同一个 GitHub 内置按钮。

### 24.1 把 GitHub 当成「产品的可追溯研发操作台」

你不需要先会 PHP、Git 命令或服务器运维，才能监督 AI 做软件研发；但必须能回答：

| 产品负责人要知道什么 | GitHub 中查哪里 | 如何判断 |
|---|---|---|
| 这轮到底要做什么？ | Issues + 已批准的 PRD / 验收文件 | 需求与验收范围确定，不是聊天随口承诺 |
| AI 实际改了什么？ | Pull requests → Files changed | 新增/删除文件、权限代码和测试是否符合约定 |
| 代码进正式研发基线了吗？ | PR 的 Merged 状态、main 提交记录 | Open PR、关闭但未合并不算进入 main |
| 代码有没有接受自动验证？ | Actions → Workflow run → Jobs / Steps | 检查本次提交对应的运行结果，不能借用旧的绿色记录 |
| 网站已经上线最新代码了吗？ | Actions 部署记录 + 服务器实际版本 | 服务器运行版本 SHA 与目标提交一致，且实际页面可用 |
| 数据库和真实数据就绪了吗？ | 独立部署/迁移/对账证据 | 不由「CI 绿」「HTTP 200」自动推导 |
| 产品真的完成了吗？ | 验收标准 + 人工产品签收 | 功能、视觉、错误处理、权限、恢复手段都满足 |

**最重要的判断公式：需求批准 ≠ 代码编写 ≠ PR 合并 ≠ CI 通过 ≠ 部署成功 ≠ 数据导入 ≠ 人工验收。**

GitHub 可以帮助把前几步记录清楚，但 GitHub 不是生产数据库，更不是产品负责人签字的替代品。

### 24.2 版本与协作：读懂分支、SHA 和 PR

| English / 术语 | 零技术基础理解 | 你需要关注的核验点 |
|---|---|---|
| HEAD / Branch head | 某条分支当前指向的最新提交 | AI 修改前先读最新 main 的 HEAD |
| Commit SHA / Commit hash | 一次代码提交的唯一内容标识 | 汇报提交的完整 SHA，而不只说「最新版」 |
| Blob SHA / File SHA | 单个 Git 文件内容的标识 | 更新共享文件前重新读取 SHA，防止覆盖并行修改 |
| Ref / Git reference | 指向分支或 Tag 的名字/引用 | main 会移动，固定 SHA 不会随新的提交漂移 |
| Base / Head branch | PR 要合入的目标分支 / 交付代码的来源分支 | PR 是从正确分支合向 main 吗？ |
| Ahead / Behind | 相对另一个分支多了 / 少了哪些提交 | 长时间开发后是否需要同步 main |
| Draft PR | 草稿合并请求 | 尚未准备好审查，不能当作交付完成 |
| Mergeable / Merge conflict | GitHub 是否能合并 / 是否有冲突 | 代码冲突要保留双方成果，不得直接覆盖 |
| Squash and merge | 把 PR 内多个开发提交整理为一个主线提交 | 合并后 main 的 SHA 可能不同于 PR 分支最后一个 SHA |
| Closed without merge | PR 关闭但没有合并 | 此 PR 的代码不一定进入 main；检查是否另有替代 PR |
| Revert | 新提交用于抵消旧提交 | 适合已共享的代码回退，但数据库/生产数据要独立恢复 |
| Force push / Force with lease | 强制改写历史 / 带预期版本约束的强制推送 | 有覆盖他人工作的风险；普通产品负责人不应随意使用 |

**实战建议**：每次让 AI 改代码，先让它给出当前 main SHA、计划影响的文件、是否存在别的对话/分支也在修改这些文件。完成后再核对 PR、合并提交 SHA 和变更文件名单。

### 24.3 CI、GitHub Actions 和「绿色对勾」到底证明什么？

**CI（Continuous Integration，持续集成）**：新代码进入协作流程时，自动运行约定的语法、测试、构建和安全检查。**GitHub Actions** 是可以运行 CI、CD、定时任务等多类自动化的工具平台，不等于 CI 本身。

| English / 术语 | 中文与用途 | 常见误区 |
|---|---|---|
| Workflow | 工作流：通常由仓库 .github/workflows 下的 YAML 文件定义 | 工作流存在 ≠ 必然被触发 |
| Trigger / Event | 触发条件，例如 push、pull_request、workflow_dispatch | 只监听 push(main) 的流程不一定会检查 PR |
| workflow_dispatch | 从 Actions 中手动触发工作流的事件 | 有配置、权限和按钮才可手动启动 |
| Runner | 真正执行自动化任务的计算环境 | GitHub 云端 runner 不等于你的生产服务器 |
| Job / Step | 一个作业 / 作业中的一步命令或操作 | 失败要定位到具体 Job → Step |
| Check run / Status check | 对某个提交给出的自动检查结果 | 别把昨天别的 commit 的绿色结果算到今天 |
| Required status checks | 配置在保护规则中的必需检查 | 未配置为必需时，CI 红也可能有人可以合并 |
| Test case / Assertion | 测试用例 / 测试中一条可验证的判断 | 70 个测试、455 次断言只覆盖写好的检查，不证明全部需求已实现 |
| Regression test | 回归测试：防止新改动破坏已有功能 | 修好新页面还要检查旧登录、授权和症状记录 |
| Smoke test | 冒烟测试：验证最基础的启动/路由/响应 | 接口 HTTP 200 不等于整套业务可用 |
| Fixture / Synthetic data | 固定测试样本 / 纯合成数据 | 不能把真实个人资料复制到公开 CI |
| Job log / Step log | 自动化日志 | 日志可能失效或不可读；此时应标「未核实」，不能猜测通过 |
| Artifact | 工作流产物，如测试报告、截图、构建包 | 产物一般有保留期限；重要证据还要记录固定引用 |
| Re-run failed jobs | 重新运行失败作业 | 适合怀疑偶发环境问题；不能代替修复可重复的代码缺陷 |
| Timeout / Cancelled / Skipped | 超时 / 已取消 / 被跳过 | 都不能算作「测试通过」 |
| Matrix strategy | 使用多组语言版本、系统或参数重复测试 | 适合不同 PHP/Node 版本或不同浏览器组合 |

**五步读懂一次 CI 失败：**

1. 进入 **仓库 → Actions**，点开与本次 PR / commit 相匹配的 workflow run。
2. 看最终的 **Conclusion**：Success、Failure、Cancelled、Skipped；**Completed 只表示结束，不表示成功**。
3. 逐个展开 **Jobs → 失败的 Step → 日志**；先找第一条可重复的根因，不盲目修改几十个文件。
4. 如果是测试断言失败，先判断**功能代码错了、测试期待过期了，还是环境配置有问题**；修复后必须重新运行全部相关测试。
5. 如果日志无法读取，记录 Run URL、时间、提交 SHA、失败状态和阻断，不得写成 passed。可再用独立、可复现的诊断工作流排查，而不是无限重试。

**例子（改写自真实协作经验）**：AI 已合并 A、B 两批功能，但 C 批上传与时间线的 CI 出现失败；即使已有 70 多个用例通过、只剩少量失败，也应保留 C 的 PR 为 Open / blocked，不能把它写入「完整产品已通过」。

### 24.4 CD、发布、迁移：为什么 CI 成功还不能说上线？

**CD** 通常指 Continuous Delivery（持续交付）或 Continuous Deployment（持续部署）。两者区别在于：交付可经人工批准后发布，持续部署则在符合条件时自动发布；**具体含义要看该仓库实际配置的流程**。

| English / 术语 | 小白解释 | 核验依据 |
|---|---|---|
| Build artifact | 可用于部署的构建成果 | 构建包来源、校验值、关联的 commit SHA |
| Deployment / Deploy job | 将程序版本放到指定环境的发布作业 | 看到 Success 仍需检查服务器实际运行版本 |
| Deployment environment | 目标环境，如 testing / staging / production | 不要把测试站当作正式生产 |
| Deployed SHA / Release SHA | 真正运行在服务器上的版本号 | 与目标 main 的提交比较，防止「代码合并但网站还是旧版」 |
| Health check | 健康检查，例如站点基本请求是否正常 | 只证明被检测的那部分响应正常 |
| HTTP status 200 / 404 / 500 | 响应成功 / 未找到 / 服务器故障等类别 | HTTP 200 也可能是错误页面，需检查实际内容 |
| Database migration | 将数据库结构升级到新版本 | 代码里有迁移文件不等于数据库实际已迁移 |
| Backup / Restore drill | 备份 / 验证备份能否真正恢复 | 有备份文件不等于恢复过；生产操作前独立核验 |
| Rollback | 发布失败后回退 | 代码回退与数据库/患者数据恢复是两套不同风险 |
| GitHub Pages | 托管静态 HTML / CSS / JavaScript | Pages 不运行任意 PHP 业务与生产 SQLite |
| Concurrency | 控制同类工作流同时运行/互相覆盖 | 防止并行部署互相覆盖，但仍要核对最终服务器版本 |

**发布最小闭环**：CI 通过 → PR 审核合并 → 指定版本部署 → 实际访问网站 → 核验运行 SHA → 检查业务接口 → 核对数据库迁移与备份/恢复 → 人工产品验收。任何一步没有证据，就标记尚未验证。

### 24.5 AI Agent 和 GitHub 的「项目记忆」：哪些是功能，哪些是管理制度？

AI 协同开发中，有些名词不是 GitHub 产品功能，而是我们自己设计的工程管理方法：

| 名词 | 类型 | 用法 |
|---|---|---|
| AI Agent / Coding Agent | AI 工程工作方式 | 读取仓库、按需求改代码、写测试并创建 PR；权限由用户和连接器决定 |
| GitHub App / Connector / MCP | 连接和授权能力 | 让聊天工具在授权范围内操作仓库；**连接上不代表拥有所有权限** |
| Source of Truth（SSOT） | 项目治理原则 | 对一个工程事实确定唯一权威来源；常用 latest main + 已批准决策 + 轮次证据 |
| AGENTS.md | 仓库内的 Agent 指南文件 | 告诉 AI 如何读项目、编程、测试、保护隐私；**不是 GitHub 自动执行指令的内置按钮** |
| PRD（Product Requirements Document） | 产品需求文档 | 定义要解决的问题、业务流程、页面与边界 |
| ADR（Architecture Decision Record） | 技术决策记录 | 解释选某个技术方案的理由及变更条件 |
| Acceptance criteria | 验收标准 | 在开工之前明确成功与失败的可判断条件 |
| Definition of Done（DoD） | 整个交付完成定义 | 包括功能、测试、权限、部署和人工确认，不是「代码已写完」 |
| Decision register | 决策登记册 | 区分已批准决定、历史变更及其适用版本 |
| Iteration ledger / ROUND.json | 团队自建的轮次账本 | 记录单轮需求、代码、CI、部署、真实数据、验收等独立状态 |
| Test evidence | 测试证据 | 记明测试结果、Run URL、提交 SHA、失败与未执行项 |
| Release facts | 上线事实 | 只记录服务器上实际发生的部署、迁移、数据对账与恢复 |
| Handoff | 研发交接 | 新聊天也能从 GitHub 找到完成项、阻断和下一步 |
| Scope freeze / Baseline | 范围冻结 / 验收基线 | 明确设计稿或原型版本，不允许 Agent 凭想象换界面 |
| Work package | 工作包 | 一个轮次内的可审查开发小块；**七个包不等于七个版本轮次** |
| Human sign-off | 产品负责人签收 | AI 和 CI 不可以替代负责人对实际体验的验收 |

**推荐的 AI 交接顺序**：读取最新 main SHA → AGENTS.md → 决策/轮次规范 → 当前轮次 ROUND/HANDOFF → PRD/验收标准 → 最近 PR/CI → 相关源码。不得只凭上一段聊天宣称「已经部署」或「已经入库」。

### 24.6 双对话并行协作：安全避免覆盖对方的成果

用 ChatGPT 同时开展「产品/研发」和「服务器/发布」两条对话是可行的，但**两个聊天窗口不会天然共享全部未提交的工作进度**。需要以 GitHub 持久记录衔接。

- 每个对话执行前重新读取 **main HEAD** 与所改文件的 SHA，不允许套用上次对话中的旧版本。
- 需要改多个文件时，先创建工作分支并通过 PR 比对差异；**不要两个对话直接反复覆盖 main 上的同一文件**。
- 原有正式决定只由新批准的决策覆盖；历史方案可保留作为审计记录。
- 研发线只记录代码、测试和交互结果；服务器线只写真实部署、迁移、恢复和运行结果，不互相推测。
- 读到更新冲突（409 Conflict）时，先获取最新文件 SHA 和差异，再人工/Agent 合并双方有效内容；不可直接强制覆盖。
- 对 AI 的「进度」只接受：Issue / PR / commit / 对应 Run / 运行环境证据。聊天里的「已完成」不能代替这些记录。

### 24.7 产品经理必会的六个小操作（不用写代码）

| 要解决的问题 | GitHub 网页路径 | 你应看到的证据 |
|---|---|---|
| 看新需求是否落地 | Repo → Issues → 任务编号 | 范围、验收、关联 PR 与当前阻断 |
| 看 AI 写了哪些代码 | Repo → Pull requests → PR → Files changed | 文件改动、删除项、是否触及敏感目录 |
| 看代码是否真的合入主线 | PR 页面 → Merged 状态 + main Commits | 合并提交 SHA，不是仅 Closed |
| 看 CI 为什么红 | Repo → Actions → Run → Jobs → 失败 Step | 失败步骤、测试用例和日志 |
| 看最新版是谁 | Repo → Code → main → Commits | 最新 SHA；再与服务器当前 SHA 比较 |
| 看网站发布 | Repo → Actions → 部署 Run；随后实际打开网站 | 部署 Success + 目标地址可用 + 版本匹配 |

### 24.8 五段可复制的「让 AI 真正执行」指令

**需求进入开发：**

> 请先读取 GitHub 最新 main 和现有 PRD/决策记录；核对当前轮次账本。按本轮验收标准执行编码、合成测试、PR 与 CI，不重新讨论已批准范围。修改前报告要影响的代码和权限边界。

**提交前核查：**

> 请列出 PR 的 Issue、变更文件、源分支和目标分支、最新 SHA、哪些测试 passed/failed/not_run；检查有没有私人数据、真实密码或无关重构，确认后再合并。

**CI 失败处理：**

> 请打开这次提交对应的 Actions Run，定位失败 Job 和 Step，先说明代码问题、测试期待问题或环境问题的证据，再做最小修复并重新运行。没有日志就记为未核实，不要盲目重复运行。

**部署与正式验证：**

> 请把「main 合并」「CI 通过」「服务器已部署 SHA」「数据库迁移」「备份恢复」「真实数据导入对账」「产品人工验收」分开报告。缺证据的状态写 not_run / not_verified，不推断成功。

**新对话交接：**

> 请从 GitHub 最新 main、AGENTS.md、轮次 ROUND.json 和 HANDOFF.md 恢复项目，先确认是否有并行 PR / 服务器变更；只处理账本中最高优先级的未完成项，并将结果写回仓库。

### 24.9 误区对照：听到这句话要追问什么？

| 常听到的说法 | 不应立刻推断 | 追问 AI / GitHub 的证据 |
|---|---|---|
| 「代码已经提交」 | 已经上线 | 是哪个 Branch / Commit？PR 合并了吗？ |
| 「PR 已关闭」 | PR 已合并 | 页面是 Merged 还是 Closed without merge？ |
| 「CI 绿色」 | 所有功能和视觉已经通过 | 该 Run 对应哪个 SHA？覆盖了哪些测试？ |
| 「70 项测试通过」 | 产品整体完成 | 失败/跳过/未运行项是什么？有人工视觉验收吗？ |
| 「部署成功」 | 服务器与数据库/数据都可用 | 服务器 current SHA、业务接口、迁移、对账分别是什么？ |
| 「HTTP 200」 | 业务正确 | 是正常业务响应吗？登录/权限/错误流程也测了吗？ |
| 「已生成账号」 | 安全交付给了使用者 | 凭据通过什么私密渠道交付？是否首次改密？ |
| 「有数据库迁移文件」 | 生产库结构已升级 | 实际执行日志、备份和迁移版本是什么？ |
| 「AI 记得之前内容」 | 对话信息比仓库更新 | 最新 main 与当前 HANDOFF 的事实是什么？ |
| 「有备份」 | 可以恢复 | 上一次真实恢复演练与结果在哪里？ |

### 24.10 一个去标识化的 AI 工程案例

某私有家庭健康应用由一位产品负责人和一个 AI Agent 协同开发。产品负责人冻结了视觉原型；AI 把需求拆成若干**工作包**，而不是在每个工作包之间新建独立产品轮次。

- **A 包**：公共介绍页和视觉框架的代码 PR 合并，自动化测试绿色。但截图对照仍标「未进行」。
- **B 包**：真实趋势与家庭记录 API 合并，CI 也通过，但这仍不是全部产品。
- **C 包**：涉及私有文件上传和病历时间线，CI 出现失败；Agent 修正旧断言后依然未能取得完整可核验的通过结果，于是 PR 保持开放，不能拿 A/B 的绿灯代表 C 已通过。
- **独立部署线**：只在核对实际部署 SHA、数据库迁移、恢复证据后记录发布事实；不能从 CI 成功推断患者资料已入库。

这说明三个方法很关键：**以证据而非口头进度管理；按工作包分 PR、按轮次统一验收；让敏感数据留在受控生产环境而不是 GitHub/CI**。

### 24.11 安全与权限：公开手册也要守住底线

公开仓库可以存放通用术语、合成样例和操作技巧，**不能放入真实患者病历、身份证明、账号密码、授权码、生产数据库、服务端 .env、备份或私有连接凭据**。即使仓库为 Private，也应避免提交这些资料：拥有仓库读取权的连接器、协作者及 CI 作业可能读取仓库内容。

用 **Least privilege（最小权限）** 控制 GitHub App、PAT、Actions Token；Secret 只是存储与注入敏感值的机制，不意味着日志里或执行脚本里不会泄露。需要主线审核时可使用 Rulesets / Branch protection / Required checks，实际是否生效取决于仓库权限与配置。

**非 GitHub 官方术语特别提醒**：SSOT、PRD、ADR、DoD、轮次账本、G0/G1/G3 这类门禁编号是工程管理方法和约定，不应误认为 GitHub 自带某个同名菜单。

## 25. GitHub Actions 免费额度耗尽：Agent 自测 → PR → 人工验收过渡方案（2026-11）

> **适用条件**：GitHub Actions 的可用额度不足，项目负责人不愿开启付费或超额账单；团队仍希望使用 ChatGPT / Codex、GitHub、GitHub Desktop 继续研发。**本章是一份可撤销的临时协作方案，不意味着已修改任何仓库的 Actions 开关或账单配置。**

### 25.1 一句话决策：停用的是自动执行，不是研发协作

**过渡主流程：产品负责人 + ChatGPT 确认需求 → Agent 在独立分支完成整轮开发和真实测试 → Agent 提交含证据的 PR → 审查与授权合并 main → GitHub Desktop Pull 最新 main → 本地运行 → 产品负责人集中人工验收。**

| 环节 | 谁负责 | 没有 Actions 还能做吗 | 产出证据 |
|---|---|---|---|
| 需求、边界、验收标准 | 产品负责人 + ChatGPT | 可以 | 一份明确任务说明 |
| 编码、修复、回归测试 | Codex / Agent | 可以，但 Agent 必须具备可执行环境 | 运行命令、测试输出、失败说明 |
| 分支、Commit、PR、合并 | Agent + GitHub（按授权） | 可以 | PR URL、Commit SHA、合并记录 |
| 本地同步源码 | 产品负责人 + GitHub Desktop | 可以 | main 的最新 SHA |
| 启动、体验和人工验收 | 产品负责人 | 可以 | 截图、验收结果、问题清单 |
| GitHub Actions 自动 CI / 自动部署 | GitHub 托管运行器 | 暂停或受限 | **不能**声称自动 CI 成功或 Pages 已更新 |

**注意**：仓库为 Public 时，符合条件的标准 GitHub 托管运行器通常免费；Private 仓库则受套餐包含额度等限制。先到 **[GitHub Billing](https://github.com/settings/billing)** 看本账号实际用量、计费规则及是否设置了超额付费；不要为了免费而把私有业务源码、患者资料或密钥改为公开。

### 25.2 立即止损：先把费用风险和阻塞处理清楚

1. **账单**：在账号 Billing / Usage、Budgets 中确认额度状态和超额消费设置；以当前官方页面及账号显示为准。过渡期间不主动开启付费，也不反复重试耗额度的失败工作流。
2. **触发器**：由有权限的仓库管理者逐一检查 Repo → Actions；仅对非必要的自动测试、重复快照和重复同步工作流选择 **Disable workflow**。先停用、不要直接删除历史 YAML 和日志。Pages 自动部署属于独立发布链路，不能在不评估影响时一并关闭。
3. **合并门禁**：检查 Settings → Rules / Rulesets / Branch protection 是否把已停用的 CI 检查设为 Required status check。若检查无法运行，PR 可能一直不能合并；必须由有管理权限的人审慎调整对应规则，保留必要的 Review 与安全限制，不建议用强制推送绕过。
4. **发布状态**：Actions 停用不影响 GitHub 托管代码、PR 或 Desktop Pull；但 Actions 驱动的 Pages 部署、自动构建、自动打包也会停止。**main 更新 ≠ Pages 更新 ≠ 本地运行通过**。需要线上发布时单独规划可用且合规的发布办法。
5. **保护现场**：记录停用前的工作流、分支规则与旧 CI 状态，方便额度恢复后逐项启用，不要顺手清理历史文档、重构目录或改动封版基线。

### 25.3 Agent 在提交 PR 前必须完成什么？

遵守 **“同类功能整合开发、一轮完整交付、集中人工验收”**，不是每改一个按钮就要求产品负责人验一次。

1. **先读再改**：确认最新 main SHA、当前需求、项目规范、不可修改区域与启动方式；新建任务分支，不在旧分支上盲改。
2. **实现与自检**：完成同类功能的本轮开发，并在 Agent 实际可用的环境中执行适合项目的静态检查、单元测试、集成/回归测试、构建、启动冒烟测试；UI 任务还要检查主要页面与 PC/H5 表现。
3. **失败先修复**：发现失败，先定位原因并修复，再在同一代码版本上重新运行相关检查；未执行的检查写明原因，不能把“计划运行”写成“通过”。
4. **核对安全与边界**：不提交真实账号密码、患者信息、.env、生产数据或备份；确认封版基线未被覆盖、无需求外重构，且提交的测试报告对应最终 PR HEAD SHA。
5. **再交付 PR**：提交一份可核验的 PR 说明；若关键测试失败或环境无法启动，PR 应标为 Draft 或明确阻塞，不能以“自测完成”申请合并。

**Agent 自测不是独立 CI 的等价替代。** 无法运行的测试、环境差异或跨模块风险，要留给后续复核和人工验收，不能假装被覆盖。

### 25.4 PR 交付证据清单（直接照此检查）

| 必填项目 | 最低要求 |
|---|---|
| 任务与范围 | 对应需求、实现功能、未做功能、保护区域 |
| 变更明细 | 分支名、PR URL、最终 HEAD SHA、改动文件及影响模块 |
| 测试环境 | 操作系统 / Node 或其他运行环境 / 依赖版本（按项目实际情况） |
| 测试记录 | **逐条命令**、执行时间或轮次、PASS / FAIL / NOT_RUN、关键输出摘要 |
| 失败与残余风险 | 未通过、跳过、无法运行的项目及原因，不得合并进 PASS |
| 运行与验收指南 | 本地启动命令、测试数据要求、需要人工查看的页面或功能 |
| 提交结论 | Ready for review 或 Draft / Blocked；不使用“CI 已通过”冒充 Agent 自测 |

**推荐 PR 状态**：Draft / Blocked（未达到自测标准）→ Ready for review（证据齐全）→ Review（核查风险、差异、必要的人工预览）→ Merge main（有授权且满足门禁）→ Product acceptance（Desktop 同步并启动验收）。PR 合并可以先于本地产品验收，但**合并不等于验收通过**；存在高风险变更时可以要求先预览测试分支，再决定是否合并。

### 25.5 产品负责人只做三件事

1. **查看 PR**：重点看改了什么、Agent 真正执行过什么测试、有无 FAIL / NOT_RUN、是否触及敏感内容、合并是否被要求的检查挡住。若证据不足，退回 Agent 补测，不必自己读全部代码。
2. **同步 main**：PR 按授权合并后，在 **GitHub Desktop** 选择正确仓库与 main，执行 **Fetch origin → Pull origin**，确认没有未处理的本地改动和冲突；只把 Desktop 当源码同步与验收辅助工具。
3. **本地验收**：以仓库记录的启动入口运行项目。例如某些 Windows Mock 项目仍使用 **START_MOCK_CENTER.cmd**；这是该类项目的示例，不是所有仓库通用命令。按验收项集中检查，发现问题形成单轮反馈交 Agent 修复并再走 PR。

### 25.6 一段可复制给 Codex / Agent 的过渡期任务指令

> 目前本项目因 GitHub Actions 免费额度限制，采用“**Agent 先开发与真实自测，再提交 PR，产品负责人集中验收**”的临时流程。请先读取仓库最新 main、现行规范、不可修改基线与本轮验收标准；在独立分支整合完成同类功能，执行当前环境能实际运行的相关检查、回归测试和启动验证。所有测试逐项记录命令、环境、最终 SHA、PASS / FAIL / NOT_RUN 和关键结果，失败先修复并复测，不能虚构 CI 成功或线上部署。PR 中说明范围、风险、未验证项、启动方式和人工验收步骤。关键测试不能通过则保持 Draft / Blocked。获授权且满足仓库合并规则后再合并 main；由我使用 GitHub Desktop 拉取 main 并在本地完成产品验收。不要为省费把私有仓库改公开，不修改生产密钥/病历数据，不擅自绕过分支保护，不增加复杂多 Agent 流程。

### 25.7 免费额度恢复：如何安全切回自动 CI？

当账单界面显示额度可用、费用设置符合预期时，由有权限的管理者逐项恢复需要的工作流：**先选一条轻量 PR 验证 → 核对真实运行结果 → 恢复必要 Required checks → 恢复其他合理的自动化任务**。按需保留 Agent 本地测试作为提交前自检，避免 CI 重复执行冗长任务。

恢复前后都要分开核对 **代码 SHA / Agent 自测 / Actions CI / PR 合并 / Pages 或服务器部署 / 产品验收** 六种不同事实；任何一项没有证据都写 **NOT_VERIFIED**，不能用另一项替代。
